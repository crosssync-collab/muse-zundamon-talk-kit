# 背面再生の限界と対策

## 課題

待機ページ（ブラウザのタブ）で待ち受ける方式は、端末の省電力制御の影響を受ける。

- 実測（REDMI Note 15 Pro 5G / MIUI）：前面表示と分割画面では安定して鳴る。完全に背面へ回すと、Chrome のタブが凍結されて合図の検知も再生も止まることがある
- タブが完全に凍結・破棄された状態では、どの Web API でもコードは動かない。対策の狙いは「メディア再生中のタブとして Chrome に扱わせ、凍結されにくくする」ことと、「切れても復帰したときに合図を取りこぼさない」ことの2点

## 実施した対策（2026-11-24）

### 1. keepalive ループの実音化

- 従来は4秒の完全無音 mp3 だった。Chrome は「5秒未満」「完全無音」のメディアを再生中と見なさず、メディア通知やバックグラウンド維持の対象にしない可能性がある
- `scripts/make_keepalive.sh` を変更：30秒・ピンクノイズ約 -60dB（聞こえないが無音ではない実音）・mp3 64kbps で生成する。生成物の実測：30.0秒、64kbps、最大音量 -61.7dB

### 2. Media Session API（両テンプレート）

- 有効化ボタンのタップ時に `navigator.mediaSession.metadata`（title「ずんだもん待機中」、artist「VOICEVOX:ずんだもん」）を設定し、`playbackState` を `"playing"` にする
- play / pause ハンドラはどちらも keepalive の再生を続ける動作にした（メディア通知やイヤホン操作で止められても居座り再生が続く）
- 「止める」ボタンでは `playbackState` を `"paused"` に戻す

### 3. keepalive の自動再開（両テンプレート）

- `visibilitychange`（背面・前面の両方向）、keepalive の `pause` イベント、5秒間隔の点検の3経路で、停止していたら再生し直す
- 従来ポーリング版だけにあった再開処理を SSE 版にも揃えた
- 他のアプリの音を邪魔しないための上限（10分間に6回まで）は両版とも維持する。上限に達したら自動再開を止め、有効化ボタンの押し直しで解除される

### 4. SSE の取りこぼし回収（SSE版と server.py）

- ハートビートは従来から実装済み（20秒ごとに `: heartbeat` コメント行）であることを確認
- 合図に連番（seq）を付け、SSE メッセージに `id:` を載せるようにした。再接続時にブラウザが送る `Last-Event-ID` を見て、切断中の合図をサーバーが再送する（直近50件まで保持）
- `GET /state` を追加。ページは再接続時・前面復帰時・読み込み時に最新合図を確認し、2分以内のものなら鳴らす
- ローカル検証済み：切断中に送った合図が再接続直後に再送されること

### 5. 診断ログ

- ページの状態変化（読み込み、有効化、背面/前面、keepalive 停止・再開、SSE 切断・再接続、合図受信など）を時刻つきでサーバーへ POST する（`POST /diag`、サーバー側 `diag.log` に JSON Lines で保存、上限1MBで自動切り詰め）
- keepalive の再生時計から60秒ごとに `alive` を送る。背面で `alive` が途切れた区間が、タブが凍結していた時間帯とみなせる
- 読み出しは `GET /diag?key=<push_key>`（キーは push と共通）
- ポーリング版は単体ファイルでサーバーを持たないため、ビルド時に診断URLを指定した場合だけ送信する（`build_standby.py` の第6引数）。未指定なら診断はページ内ログのみ

## 実機での確認結果

2026-11-24、REDMI Note 15 Pro 5G で確認した。

- ポーリング版（新テンプレートでビルドした単体ページ）：前面での再生と keepalive の継続を確認
- **完全背面に回して約5分後に送信した合図が、自動で再生された**（従来は完全背面で止まっていた）
- **完全背面で約10分後、さらに端末の画面が消灯した状態でも、合図が自動で再生された**（同日12:03のテスト）
- 上記はいずれも、端末設定（Chrome の電池「制限なし」、MIUI の自動起動許可）を**変更していない**状態での結果。つまり今回のコード側の対策だけで効いている
- 残りの確認：数十分単位の背面持続。端末設定を変えた場合との差は未測定（変えなくても動作しているため、設定変更は長時間化したときの追加の安全策という位置づけ）

鳴らなかった場合の切り分け手順：診断ログを見て、凍結（alive の空白）か、切断（sse-error）か、再開上限（resume-capped）かを確認する。

## 効果が足りない場合の段階的な次手（未実施）

1. **PWA（ホーム画面に追加）として起動**：スタンドアロン起動はタブより破棄されにくい場合がある。SSE 版はサーバー配信なので manifest と Service Worker を足せば成立する
2. **Web Locks API**：常駐ロックでページの生存を主張する。凍結そのものを防ぐ保証はない
3. **再生中の音声要素を1つに集約**：フレーズ再生と keepalive を単一の `<audio>` にまとめ、メディアとしての存在感を切らさない
4. その他、タブ凍結を避ける公開 API の範囲の手段

## 残る制約

- タブが完全に破棄された場合、その間の合図は（SSE 版の再送でも）ページ再読み込みまで鳴らない。再読み込み後は `/state` の確認で2分以内の合図だけ拾う
- 最初の再生は自動再生制限のため、必ず利用者の有効化タップが起点になる
- 端末ベンダーの省電力制御（MIUI 等）は OS バージョンで挙動が変わるため、上記の実機確認が前提になる

## 本気で背面再生を狙う場合の代替案（対象外・検討メモ）

ブラウザタブ方式を維持する方針のため今回は対象外だが、過去の検討として残す。

1. **ネイティブアプリ経由（Tasker 等）**：プッシュ通知や HTTP リクエストをトリガに音声ファイルを再生する。端末側の常駐が必要
2. **メッセージング Bot から音声を送る（Telegram Bot 等）**：合図のたびに Bot が音声メッセージを送信する。通知音として届く形になる
3. **SSE / WebSocket + ネイティブシェル**：待機ページを WebView アプリに包み、フォアグラウンドサービスで接続を維持する
