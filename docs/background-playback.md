# 背面再生の限界と代替案

## 現方式の限界

待機ページ（ブラウザのタブ）で待ち受ける方式は、端末の省電力制御に勝てない。

- 実測（REDMI Note 15 Pro 5G / MIUI）：前面表示と分割画面では安定して鳴る。完全に背面へ回すと、Chrome のタブが凍結されて合図の検知も再生も止まる
- 無音ループ再生による居座り、ポーリング間隔の短縮などを試したが、完全背面での安定動作には至らなかった
- Chrome の電池制限を「制限なし」に変える案は未検証

利用者の判断として「スマホを触ってやり取りしている間に鳴ればよい」が要件であり、現方式はその範囲では実用になっている。

## 本気で背面再生を狙う場合の代替案（未実装・検討メモ）

1. **ネイティブアプリ経由（Tasker 等）**：プッシュ通知や HTTP リクエストをトリガに、Tasker で音声ファイルを再生する。端末側の常駐が必要で、導入コストは高いが背面制御を回避しやすい
2. **メッセージング Bot から音声を送る（Telegram Bot 等）**：合図のたびに Bot が音声メッセージを送信する。通知音として届く形になるが「返信に合わせて声が鳴る」体験とは少し違う
3. **SSE / WebSocket + ネイティブシェル**：待機ページを WebView アプリに包み、フォアグラウンドサービスで接続を維持する。自作アプリの配布と署名が必要

いずれも「ブラウザのタブだけで完結する」という現方式の手軽さと引き換えになる。必要になったら、この順で検討するのが現実的だと考えている。
